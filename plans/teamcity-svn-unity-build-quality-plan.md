# Unity + SVN + TeamCity 大型项目构建质量治理方案草案

> 本文档用于持续迭代客户当前大型 Unity 游戏项目的构建质量问题、错误收束策略、CI 验证策略与责任定位方案。
>
> 当前约束：不调整现有 SVN 分支开发模式。团队已经适应当前分支流程，因此本文档不以“改变分支模型”为前提，而是在现有 SVN 分支 + TeamCity 打包 + Lark Bot 通知体系上增量改造。
>
> **AgentCore WorkspaceRoot 对齐说明（2026-06-02）**: 本文档属于外部客户构建质量治理草案，文中的 `Assets/...` 路径是 CI 规则示例，不代表 AgentCore 的全局能力边界。AgentCore 当前企业级插件规划必须以 **SVN 工作副本根 = WorkspaceRoot** 为默认边界，并把 Unity 工程目录视为 WorkspaceRoot 下的 UnityRoot 子根；CI 规则后续接入 AgentCore 时应改为 WorkspaceRoot-relative，并支持 `unity/Assets/...`、`gamemodes/...`、`tools/...` 等 Scope Root。

## 1. 背景

客户正在开发一个大型 Unity 游戏项目，团队规模约一百多人，使用：

- SVN 作为版本控制系统。
- TeamCity 作为打包与构建平台。
- Lark Bot 获取 TeamCity 错误信息并通知相关开发者。
- 每个版本更新节点前，SVN 会创建版本分支。
- 开发者需要拉取新分支，并将相关改动合并到 main 主线或版本线中。
- 游戏模式、地图、分线和资源体量较大，无法要求所有开发者全量下载所有资源资产。
- 也无法为每个分支都部署完整编译和打包验证环境。

当前核心痛点：

1. 完整包体构建耗时约 1.5 小时。
2. 经常在构建后期才发现编译或打包错误。
3. 开发者本地没有报错，但 TeamCity 构建报错。
4. Lark Bot 目前只能通知本次打包涉及的所有 changelist 提交者。
5. Bot 无法准确定位具体错误原因、具体文件、具体提交、具体责任人。
6. 大量无关人员被通知，真正责任人仍需人工排查。
7. 错误发现时间太晚，导致项目管理组、构建机、开发者时间被浪费。

## 2. 当前暂不考虑的方向

### 2.1 不调整 SVN 分支开发模式

当前团队已经适应现有分支工作流，因此本文档暂不讨论以下方向：

- 改为 Git。
- 改为 trunk-based development。
- 减少版本分支。
- 要求所有开发者统一在 main 上开发。
- 大规模重构分支策略。

后续所有方案默认基于现有 SVN 分支模式进行增量增强。

## 3. 核心判断

当前问题不是单纯的“Bot 通知不准”，而是构建质量反馈链路过晚。

现状可以抽象为：

```text
开发者提交
  → SVN 分支集成
  → 项目管理组申请 TeamCity 打完整包
  → 构建 1.5 小时
  → 后期失败
  → Bot 通知本次构建涉及的所有提交者
  → 人工排查真正原因
```

问题集中在三个层面：

1. **错误发现太晚**：完整包构建成了第一道有效质量门。
2. **错误定位太粗**：只知道“这次包失败了”，不知道“哪个文件、哪个 revision、哪个人、哪个模块导致失败”。
3. **错误类型未收束**：不同错误混在完整构建日志中，缺少结构化分类、统计和自动归因规则。

建议目标不是一次性替换现有流程，而是新增一套分层验证与归因机制：

```text
提交/集成
  → 快速验证
  → 资源与配置校验
  → 变更影响分析
  → 局部构建或目标验证
  → 完整包体构建
  → 构建失败归因与通知
```

## 4. 关于“快速编译”的定位

### 4.1 快速编译不能完整发现所有问题

快速编译不是完整构建的替代品。

它不能保证发现所有 Unity 项目构建问题，尤其不能完整覆盖：

- 平台特定构建错误。
- IL2CPP 后端错误。
- Android/iOS/Xbox/PlayStation 等平台 SDK 错误。
- Shader 平台变体错误。
- AssetBundle/Addressables 构建错误。
- 资源依赖缺失。
- 场景加载时才出现的问题。
- 构建管线后处理脚本错误。
- 运行时初始化错误。
- 只有特定地图、模式、分线组合才触发的问题。

因此，快速编译只能作为第一层快速失败机制，而不能作为最终质量保证。

### 4.2 快速编译的价值在于“提前过滤一部分必然失败”

快速编译的目标不是“完整发现所有问题”，而是快速发现那些不需要等 1.5 小时完整包构建就能发现的问题。

典型可发现问题包括：

- C# 编译错误。
- asmdef 引用错误。
- 命名空间或类型缺失。
- 方法签名变更导致的调用错误。
- Editor 脚本编译错误。
- 条件编译宏缺失导致的编译错误。
- 包依赖缺失导致的编译错误。
- 基础 Unity API 调用错误。

如果这类错误本来会导致完整包失败，那么它们应该在 5-15 分钟内暴露，而不是等完整包 1.5 小时后才暴露。

### 4.3 为什么开发者本地没有报错，但 TeamCity 会报错

理论上，如果开发者本地拥有完整相同环境、完整相同资源、完整相同平台配置、完整相同分支状态，那么很多编译错误本地确实应该能发现。

但大型 Unity 项目中经常存在差异：

#### 4.3.1 本地资源不完整

由于项目资源巨大，开发者不会全量下载所有地图、模式、分线资产。

结果是：

- 本地只验证了自己有的资源。
- TeamCity 构建使用了更多资源集合。
- 某些资源引用、场景、Bundle 配置只在构建机上暴露问题。

#### 4.3.2 本地分支状态不一致

开发者本地可能不是 TeamCity 实际构建的 revision 集合。

常见情况：

- 本地没有更新到最新。
- 本地有未提交修改。
- 本地只合了部分分支变更。
- TeamCity 构建包含多个开发者提交的组合。
- 错误来自多个提交之间的交互，而不是单个开发者本地改动。

#### 4.3.3 本地平台和构建目标不同

开发者本地通常只在 Editor 下编译，或者只验证 PC 编辑器环境。

TeamCity 可能构建：

- Android。
- iOS。
- Windows Player。
- IL2CPP。
- Mono。
- 特定渠道包。
- 特定 scripting define。

这些差异会导致本地不报、构建机报。

#### 4.3.4 条件编译宏不同

Unity 项目中经常存在：

- `UNITY_ANDROID`
- `UNITY_IOS`
- `ENABLE_IL2CPP`
- 渠道宏。
- 分线宏。
- 内部测试宏。
- Release/Debug 宏。

本地没有启用对应宏时，相关代码路径不会参与编译。

#### 4.3.5 构建管线执行了本地不会执行的步骤

完整构建可能包含：

- 资源打包。
- Addressables 构建。
- AssetBundle 构建。
- 加密/压缩。
- 热更资源生成。
- 版本配置生成。
- Lua/脚本转换。
- 代码生成。
- 后处理脚本。
- 上传制品。

这些步骤本地通常不会完整执行。

#### 4.3.6 Unity Library、缓存和导入状态不同

本地 Unity Library 可能已有旧缓存，构建机可能是干净导入或不同缓存。

这会导致：

- 本地看似正常。
- 构建机重新导入时暴露 importer 错误。
- meta 或 GUID 问题在本地缓存中被掩盖。

### 4.4 快速编译会有遗漏，但仍然值得做

快速编译一定会有遗漏。

但它能将错误分层：

| 验证层 | 能发现的问题 | 不能发现的问题 | 目标 |
|---|---|---|---|
| 快速编译 | C#、asmdef、Editor 编译错误 | 资源构建、平台构建、运行时错误 | 快速失败 |
| 资源基础校验 | Missing Script、Meta、GUID、引用缺失 | 完整平台构建错误 | 提前发现资源问题 |
| 局部构建 | 指定地图、模式、Bundle 问题 | 全量组合问题 | 缩小验证范围 |
| 完整包构建 | 最终包体问题 | 少量运行时深层问题 | 发布候选验证 |

所以快速编译不是为了取代完整包构建，而是为了减少明显错误进入完整构建的概率。

## 5. 建议的分层验证体系

### 5.1 Level 1：快速编译验证

目标：在 5-15 分钟内发现基础编译错误。

触发时机：

- 每次提交后。
- 每批 changelist 集成后。
- 完整包构建申请前。

验证内容：

- Unity BatchMode 打开项目。
- C# 编译。
- asmdef 引用检查。
- Editor 脚本编译。
- 关键 scripting define 组合编译。
- 收集 Console Error。

输出：

- 是否通过。
- 编译错误列表。
- 错误文件。
- 错误行号。
- 错误类型。
- 相关 SVN revision。
- 疑似责任人。

### 5.2 Level 2：资源基础校验

目标：提前发现常见 Unity 资源问题。

验证内容：

- Missing Script。
- Missing Reference。
- Prefab 引用缺失。
- Scene 引用缺失。
- 资源和 `.meta` 是否成对存在。
- GUID 是否重复。
- 引用 GUID 是否无法解析。
- 路径大小写冲突。
- Addressables/AssetBundle 基础配置错误。

触发策略：

- 只扫描本次 changelist 涉及资源。
- 对高风险路径做扩大扫描。
- 对公共配置变更做全量扫描。

### 5.3 Level 3：变更影响范围验证

目标：根据本次提交影响范围选择最小必要验证集。

示例：

| 变更路径 | 验证策略 |
|---|---|
| `Assets/Scripts/Battle/**` | 编译 + 战斗相关测试 |
| `Assets/Maps/Map_101/**` | Map_101 场景加载 + Map_101 Bundle 构建 |
| `Assets/GameModes/PVP/**` | PVP 模式资源校验 + PVP smoke test |
| `Assets/Addressables/**` | Addressables 配置校验 + 相关 group 构建 |
| `ProjectSettings/**` | 高风险，全量或准全量验证 |

### 5.4 Level 4：完整包体构建

目标：最终验证包体可构建、可发布。

完整包体构建仍然必要，但应该被放在最后。

建议完整包体构建前增加准入条件：

- 最近一次快速编译通过。
- 最近一次资源基础校验通过。
- 本次 changelist 没有阻塞级问题。
- 高风险路径变更已被确认。
- 构建参数完整。
- 版本配置完整。

## 6. 构建失败归因系统

### 6.1 当前 Bot 的问题

当前 Lark Bot 的逻辑近似为：

```text
构建失败
  → 获取本次构建包含的 changelist
  → 获取 changelist 中所有提交人
  → 全部 @
```

这会导致：

- 通知范围过大。
- 真正责任人不一定优先看到。
- 无关人员被频繁打扰。
- 项目管理组仍需人工排查。
- Bot 没有形成知识沉淀。

### 6.2 建议升级为归因器

目标逻辑：

```text
构建失败
  → 拉取 TeamCity 日志
  → 识别错误类型
  → 提取错误文件/资源/GUID/模块
  → 匹配 SVN revision
  → 匹配路径 owner
  → 输出疑似责任人和证据链
  → Lark 精准通知
```

### 6.3 错误类型规则库

初期可以先做规则，不必直接依赖 AI。

| 错误特征 | 错误类型 | 归因策略 |
|---|---|---|
| `error CS\d+` | C# 编译错误 | 定位 `.cs` 文件最近修改 revision |
| `Missing Script` | Prefab/Scene 脚本缺失 | 定位 Prefab/Scene 最近修改人 |
| `GUID .* not found` | GUID 缺失 | 定位引用文件与缺失资源 |
| `Duplicate GUID` | GUID 冲突 | 定位冲突 meta 文件 |
| `Addressables` + `Duplicate` | Addressables 地址冲突 | 定位 Addressables group 配置 |
| `Shader error` | Shader 编译错误 | 定位 shader/hlsl 最近修改人 |
| `BuildPipeline.BuildPlayer` | 构建管线错误 | 定位构建脚本或配置变更 |
| `PostProcessBuild` | 后处理错误 | 定位后处理脚本或平台配置 |

### 6.4 Bot 通知内容建议

通知不应只说“构建失败”，而应包含：

- 构建编号。
- 分支。
- revision 范围。
- 错误类型。
- 错误摘要。
- 疑似文件。
- 疑似 revision。
- 疑似责任人。
- 相关模块 owner。
- 证据链。
- 建议处理方式。
- TeamCity 日志链接。

示例：

```text
构建失败：Build #12345
分支：release/xxx
错误类型：C# 编译错误
疑似文件：Assets/Scripts/Battle/DamageSystem.cs
错误：CS1061 xxx does not contain definition for yyy
疑似提交：r123456 by 张三
影响模块：Battle
建议处理：检查接口变更后调用方是否同步修改
日志：<TeamCity URL>
```

## 7. 变更影响范围分析

### 7.1 目标

根据本次 SVN changelist 自动判断：

- 改了哪些模块。
- 影响哪些地图。
- 影响哪些玩法模式。
- 是否涉及公共资源。
- 是否涉及高风险配置。
- 应该运行哪些验证任务。
- 构建失败后应该优先通知谁。

### 7.2 路径到模块的归属表

建议维护一个仓库内配置文件，描述路径归属和验证策略。

示例：

```yaml
rules:
  - path: Assets/Maps/Map_101/**
    module: Map_101
    owners:
      - map_team_a
    validations:
      - scene_load
      - bundle_build

  - path: Assets/Scripts/Battle/**
    module: Battle
    owners:
      - battle_team
    validations:
      - compile
      - battle_smoke_test

  - path: ProjectSettings/**
    module: GlobalSettings
    owners:
      - engine_team
    validations:
      - full_preflight
      - build_config_check
```

### 7.3 风险分级

建议将 changelist 分为风险等级：

| 风险等级 | 示例 | 策略 |
|---|---|---|
| Low | 文档、非构建资源说明 | 可跳过重验证 |
| Medium | 普通 prefab、UI、局部资源 | 局部资源校验 |
| High | 脚本、asmdef、Addressables、地图场景 | 编译 + 局部构建 |
| Critical | ProjectSettings、Packages、构建脚本 | 准全量或全量验证 |

## 8. 错误与需求收束方式

后续建议持续收集真实失败案例，并按统一格式沉淀。

### 8.1 失败案例记录模板

```text
案例编号：BUILD-FAIL-0001
发生时间：
TeamCity Build：
SVN 分支：
Revision 范围：
构建目标：
失败阶段：编译 / 资源导入 / Bundle / BuildPlayer / 后处理 / 上传
错误摘要：
完整日志链接：
最终根因：
责任文件：
责任 revision：
责任人：
是否本地可复现：是 / 否 / 未知
本地未发现原因：
应该由哪一层验证提前发现：

```

### 8.2 统计维度

建议每周统计：

- 构建失败次数。
- 平均发现时间。
- 平均定位时间。
- Top 10 错误类型。
- Top 10 高风险路径。
- Top 10 高频失败模块。
- Bot 归因准确率。
- 无关通知人数。
- 完整包构建被早期校验拦截的次数。

## 9. 分阶段落地计划

### 9.1 第一阶段：日志结构化与错误分类

目标：先知道“到底经常错在哪里”。

工作项：

1. 接入 TeamCity 构建日志导出。
2. 建立错误正则规则库。
3. 将错误分类为编译、资源、Bundle、Shader、构建管线等。
4. 输出结构化错误报告。
5. Lark Bot 通知中增加错误类型和疑似文件。

验收标准：

- 能解析最近 20 次失败构建日志。
- 至少覆盖 60%-70% 高频错误类型。
- Bot 通知不再只有“构建失败”，而有错误摘要和疑似文件。

### 9.2 第二阶段：快速编译与基础资源校验

目标：将一部分失败从 1.5 小时提前到 5-20 分钟。

工作项：

1. 新增 TeamCity Fast Validation 构建配置。
2. Unity BatchMode 执行编译验证。
3. 增加 Missing Script / Missing Reference 校验。
4. 增加 meta / GUID 基础校验。
5. 完整包构建前检查 Fast Validation 状态。

验收标准：

- C# 编译错误能在 5-15 分钟内暴露。
- 常见 Missing Script 能在完整包构建前暴露。
- 至少拦截一部分原本会进入完整包构建的失败。

### 9.3 第三阶段：SVN 变更影响范围分析

目标：减少无效验证和无效通知。

工作项：

1. 获取构建对应 SVN revision 范围。
2. 获取 revision 中变更文件列表。
3. 建立路径到模块/owner 的归属表。
4. 根据变更文件决定验证任务。
5. 构建失败时按文件和 owner 精准通知。

验收标准：

- 每次构建能输出影响模块列表。
- Bot 能区分疑似责任人、模块 owner、构建申请人。
- 无关通知人数明显下降。

### 9.4 第四阶段：局部构建与高级归因

目标：从“发现错误”走向“定位原因”。

工作项：

1. 支持地图级别场景加载测试。
2. 支持模式级别 smoke test。
3. 支持 Bundle/Addressables 局部构建。
4. 引入历史失败案例库。
5. 对疑似 root cause 进行排序。
6. 可选引入 AI 做日志摘要和候选原因解释。

验收标准：

- 常见资源问题能定位到具体文件。
- 常见编译问题能定位到具体 revision。
- 构建失败定位时间明显下降。

## 10. 当前需要补充确认的问题

为了继续收束方案，需要补充以下信息：

### 10.1 资源与构建管线

1. 当前使用 Addressables、AssetBundle，还是自研资源打包管线？
2. 是否有热更资源构建流程？
3. 地图、模式、分线资源是否有明确目录规范？
4. 构建失败主要集中在哪些阶段？
5. 最近一个月失败最多的错误类型是什么？

### 10.2 TeamCity

1. TeamCity 构建是否每次 clean checkout？
2. 构建 workspace 是否复用？
3. 是否使用 Unity Accelerator 或 Cache Server？
4. 1.5 小时主要耗时在哪里？
5. 构建日志是否可以完整导出？

## 11. 当前初步结论

在不改变 SVN 分支开发模式的前提下，建议优先建设三件事：

1. **错误日志结构化**：先把 TeamCity 失败日志解析成错误类型、文件、阶段、模块。
2. **快速失败验证**：新增快速编译和基础资源校验，用于提前拦截明显错误。
3. **构建失败归因**：基于错误文件、SVN revision、路径 owner，将 Bot 从广播器升级为归因器。

快速编译不能完整发现所有问题，也一定会有遗漏。

但它的价值是：把一批本来要等 1.5 小时才发现的编译类错误，提前到 5-15 分钟暴露；同时为后续归因系统提供结构化输入。

最终目标不是消灭完整包构建，而是让完整包构建尽量只承担最终确认职责，而不是承担第一道错误发现职责。
