# AgentCore Unity v1.10.0 — 系统能力上限与健壮性评估

**评估时间**: 2026-07-24  
**评估方法**: 代码库全面审计 + 架构层能力盘点

#### B. 上下文感知能力

**已实现的感知维度**:
- ✅ **代码库全量索引** — SQLite + Roslyn + FTS5，支持符号查找/引用查找/文本搜索
- ✅ **文件变更追踪** — FileChangeTracker 记录本会话所有工具修改
- ✅ **控制台错误感知** — ConsoleErrorCapture 工具执行期间捕获 error
- ✅ **编译错误感知** — CompilationWatcher 编译完毕后回收错误
- ✅ **场景选中感知** — 通过 Ctrl+Shift+X 快捷键将当前 Selection 注入到 Chat
- ✅ **多会话记忆** — Mem0 长期记忆 (跨 session) + LightRAG 知识图谱 (RAG)
- ✅ **Domain Reload 生存** — 编译后所有状态可通过 SessionState 恢复

### 2.2 有能力上限的场景 (可以做但有约束)

#### C. 主动开发 (Agentic Mode) — ⭐⭐⭐⭐

**能做到什么** (给定明确任务，Agent 能自主完成的复杂度):

| 复杂度级别 | 示例任务 | 预期成功率 |
|----------|---------|-----------|
| **L1 单文件修改** | "在 PlayerController 里加一个 Dash 方法" | 95%+ |
| **L2 跨文件重构** | "把 GameManager.Singleton 换成 DI 注入" | 80% |
| **L3 新特性实现** | "加一个技能冷却 UI，绑定到 GameEvents" | 70% |
| **L4 端到端开发** | "实现一个物品拾取系统 (Component + Prefab + UI)" | 50-60% |
| **L5 复杂系统** | "从零实现一个 RPG 库存系统 (数据 + UI + 序列化)" | 30-40% |
| **L6 架构级** | "重构整个 ECS 数据流" | 10-20% |

**成功率随复杂度衰减的原因**:
1. **LLM 上下文窗口** — 200K tokens ≈ 50K 行代码，超过就必须压缩，失真
2. **工具调用轮次上限** — `maxToolCallRounds` (默认 50)，超过强制退出
3. **单工具失败重试** — `toolFailBlockThreshold` (默认 3 次失败即封禁该工具)
4. **上下文压缩失真** — 长对话压缩后细节丢失

#### D. 明确的能力上限 (受 LLM 制约)

| 场景 | 上限来源 | 上限值 |
|-----|---------|-------|
| 大文件一次性修改 | LLM 上下文窗口 | ~5000 行代码 (受 output token 限制) |
| 单轮工具编排 | LLM 推理深度 | 5-10 步链式操作 |
| 多轮对话记忆 | 上下文压缩失真 | ~20 轮清晰 / ~50 轮压缩后 |
| 跨会话记忆 | Mem0 语义检索精度 | 关键决策/偏好可靠，具体代码细节不可靠 |
| 复杂算法生成 | LLM 训练数据 | 教科书算法 OK，前沿算法不可靠 |
| 大规模并行 | Agent 循环是串行 | 单次会话内串行执行 |

### 2.3 不能做的场景

| 场景 | 原因 | 替代方案 |
|-----|------|---------|
| 真实运行时性能调优 | 只能在 Editor 内运行，无 Player Build 反馈 | 需要 Cloud Build + 人工 |
| GPU/Shader 深度调优 | 无 RenderDoc / Nsight 集成 | Frame Debugger (v1.10.x G03) |
| 平台特定 native code 编译 | 无跨平台编译环境 | 需要 CI + 人工 |
| 版本控制冲突解决 | VCS 集成只做展示，不做智能合并 | 手动 merge |
| 长任务后台执行 | Editor 关闭即结束 | 需要独立进程 |
| 团队协作 | 单机 Agent | Phase 8 MCP Server 会解决 |
| 项目从零搭建 | 无 Project Wizard | 需要用户手动 Unity Hub 创建 |

## Part 3 — 健壮性分析

### 3.1 多层容错设计

**Agent Loop 层** ([`AgentLoop.Runner.cs`](Packages/com.agentcore.unity/Editor/Core/AgentLoop.Runner.cs:32)):

```csharp
// 1. 最大轮次保护
int maxRounds = settings.maxToolCallRounds;  // 默认 50
while (currentRound < maxRounds) { ... }

// 2. Token Budget 保护
if (tokenBudget > 0 && accumulatedTokens >= tokenBudget) break;

// 3. 连续全失败检测 (两级)
int allToolsFailBlockThreshold = Math.Max(2, settings.allToolsFailBlockThreshold);

// 4. 单工具失败追踪
int toolFailBlockThreshold = Math.Max(2, settings.toolFailBlockThreshold);

// 5. 同一目标重复调用检测 (防死循环)
const int toolTargetRepeatBlockThreshold = 7;

// 6. Cancellation Token 全链路传递
if (ct.IsCancellationRequested) break;

// 7. WaitingForClarification 状态强制退出
if (CurrentState == AgentState.WaitingForClarification) { ... }

// 8. ask_user 挂起截断
if (!string.IsNullOrEmpty(_pendingUserInputToolCallId)) return;
```

**工具执行层**:
- ✅ 每工具 try-catch 包裹，异常转 ToolResult.Fail
- ✅ 参数 Schema 预校验 (ToolParameterValidator)
- ✅ 主线程 marshaling 自动处理 (RequiresMainThread)
- ✅ Undo 契约强制 (34 mutating 工具全覆盖)

**LLM 请求层**:
- ✅ FallbackRouter — 失败自动降级到备用模型
- ✅ Reasoning tier escape — 高级模型专用于复杂推理
- ✅ SSE 流式解析 + 部分结果保存 (中断也不丢失)

**Domain Reload 层**:
- ✅ DomainReloadState 通过 SessionState 序列化
- ✅ 编译中断的对话恢复继续

### 3.2 安全策略层

**三级风险控制**:

| 级别 | 触发条件 | 用户体验 |
|-----|---------|---------|
| **Allow** | 只读 action + 低风险能力 | 直接执行 |
| **RequireConfirmation** | High/Destructive/CodeExecution + write/delete 类 action | 弹确认卡片 (3 按钮) |
| **Block** | Workspace 路径为 Blocked | 直接拒绝 |

**Capability 位掩码** ([`ToolCapability.cs`](Packages/com.agentcore.unity/Editor/Tools/Safety/ToolCapability.cs)):
- WriteProjectFiles / DeleteProjectFiles / ModifyScene / ModifyAssets / ModifyScripts / ExecuteCode / InstallPackages / BuildPlayer / NetworkAccess / VersionControlWrite / ModifyProjectSettings / ModifyAgentConfig — 12 类能力位

**信任升级机制**:
- SessionLowMediumRisk — 本会话内 Low/Medium 直通
- SessionAll (YOLO) — 本会话全直通
- 每次 Domain Reload 后重置

### 3.3 execute_code 沙箱

**危险模式黑名单** ([`ExecuteCodeTool.cs`](Packages/com.agentcore.unity/Editor/Tools/Native/Scripting/ExecuteCodeTool.cs:177)):
- Process.Start / File.Delete / AppDomain.Unload 等强制拒绝
- 不支持 async/await / 顶层 return / C# 8+ 部分语法
- 编译错误精确分类 (CS-error 才 fail，warning 不阻塞)
- Debug.Log 输出自动捕获
- 依赖 Mono.CSharp.Evaluator (Unity 内置)

## Part 4 — LLM 依赖度与能力上限

### 4.1 "LLM 性能上限是否就是它的能力上限"？

**答案**: **不是**。LLM 性能是**主要瓶颈但不是唯一瓶颈**。

**能力上限的三层结构**:

```
┌─────────────────────────────────────────────────┐
│  L3: LLM 理解与生成能力 (最主要瓶颈)              │
│  - 推理深度 / 上下文窗口 / 训练数据覆盖             │
│  - 决定了任务复杂度上限                            │
├─────────────────────────────────────────────────┤
│  L2: Agent 编排层 (第二瓶颈)                     │
│  - 工具组合能力 / 循环控制 / 错误恢复策略           │
│  - AgentCore 在这层做得很好                       │
├─────────────────────────────────────────────────┤
│  L1: 工具能力层 (基础，已 88.7% 覆盖)              │
│  - 54 工具 + execute_code 兜底                    │
│  - 几乎不是瓶颈                                    │
└─────────────────────────────────────────────────┘
```

**分维度分析**:

| 维度 | 谁决定上限 | AgentCore 已做的优化 |
|-----|-----------|---------------------|
| 单工具执行准确度 | 工具实现质量 | ✅ 34 mutating 工具全 Undo + 参数校验 + 错误分类 |
| 工具选择准确度 | LLM + SOUL 提示 | ✅ SOUL §2.13 tool discovery hints (11 映射) |
| 多轮任务规划 | LLM 推理 | ✅ Self-Challenge 中途澄清 + 循环保护 |
| 大代码库理解 | LLM 上下文窗口 | ✅ SQLite 索引 + 符号搜索避免全文喂给 LLM |
| 长会话连贯性 | LLM 上下文 + 压缩 | ✅ 双压缩 (对话 + 工具结果) + Mem0 长期记忆 |
| 错误恢复 | Agent 层 | ✅ FallbackRouter + 单工具重试限制 |
| 危险操作防护 | Agent 层 | ✅ 三级风险策略 + 确认卡片 + Undo 契约 |

**AgentCore 的定位**: 把 LLM 的 "语言智能" 和 "工具智能" 的桥接做到极致，让 LLM 的能力**能有效落地到 Unity 项目**。

### 4.2 换个更强的 LLM 会怎样？

**假设** (用 Claude 4 Opus / GPT-5 / o1 顶级模型):

| 能力维度 | 现状 (GPT-4o/Claude 3.5) | 顶级模型加持后 |
|---------|--------------------------|---------------|
| L4 端到端开发成功率 | 50-60% | 70-85% |
| L5 复杂系统成功率 | 30-40% | 55-70% |
| L6 架构级成功率 | 10-20% | 30-45% |
| 单次任务链式深度 | 5-10 步 | 15-20 步 |
| 代码理解范围 | 50K 行 | 200K+ 行 |
| 长对话可靠性 | ~20 轮 | ~50 轮 |

**结论**: 换更强 LLM 会**显著提升能力上限**，但不会突破以下硬约束:
- Unity Editor 单线程 (工具串行执行，无法真并行)
- Domain Reload 中断 (编译后必然重启)
- 平台限制 (不能跨 Editor / Player 界)
- 工具颗粒度 (需要工具覆盖的 API 才能操作)

### 4.3 最复杂能做到什么

**理论上限场景** (给定顶级 LLM + 充足预算):

**Scenario A: "为项目添加一个多人组队匹配系统"**

- ⚠️ 集成测试跨 session 记忆挑战

## Part 5 — 缺陷与改进方向

### 5.1 已识别的架构缺陷

| 缺陷 | 影响 | 优先级 | 修复难度 |
|-----|------|-------|---------|
| **主线程流式期阻塞** (v1.8.5 未定论根因) | 大对话时 Editor 卡顿 | 中 | 高 (Silent 模式作 workaround) |
| **单会话内工具串行** | 无法并行调用工具 | 低 | 中 (batch_execute 部分缓解) |
| **G01/G02 profiler 深度未做** | 无法多帧时序采样 | 中 | 低 (v1.10.1 计划) |
| **G03 FrameDebugger 未做** | 无法诊断 GPU 侧 | 低 | 中 (v1.10.x 计划) |
| **G10 URP VolumeProfile 未做** | 无法改后处理 | 低 | 中 (v1.10.x 计划) |
| **Smoke test 覆盖不足** | v1.10.0 新工具未真实调用验证 | 中 | 低 (需人工/自动化) |
| **MCP Server 未做** | 无法从 IDE/CLI 外部调用 | 中 | 高 (Phase 8) |

### 5.2 潜在的系统性风险

1. **反射依赖脆弱** — G02 (v1.8.0) / G04 (v1.10.0) 走反射，Unity 版本升级可能 API drift
   - 缓解: 3 轮反射探测流程 + graceful fail
   
2. **上下文压缩失真** — 长会话压缩后细节可能丢失
   - 缓解: Mem0 长期记忆 + 关键决策显式记录
   
3. **LLM Prompt Injection** — 恶意 tool 输出可能污染上下文
   - 缓解: Sanitization 层 (`AgentLoop.Sanitization.cs`)
   
4. **工具描述关键词不覆盖** — 用户措辞与工具描述不匹配 → agent 找不到工具
   - 缓解: SOUL §2.13 tool discovery hints + Description 关键词优化

### 6.2 差异化优势

**AgentCore 的核心竞争力**:

1. **Unity 深度集成** — 直接嵌入 Editor，无进程隔离开销
2. **工具颗粒度极细** — 54 个专用工具 vs 通用 MCP 的 file/terminal
3. **Undo 契约全覆盖** — 34 mutating 工具全部保证可 Ctrl+Z 回滚
4. **上下文感知** — Scene Selection / Console errors / Compile status 原生感知
5. **Self-Challenge** — Intent 澄清 + Answer 自校验，减少无效对话
6. **代码索引原生** — SQLite + Roslyn，无需外部服务
7. **中文 first** — SOUL/UI/错误消息全部中英双语

**AgentCore 的劣势**:

1. **仅限 Unity 项目** — 无法通用编程
2. **单机运行** — 无团队协作 (待 Phase 8 MCP)
3. **单会话串行** — 无法并行执行 (Editor 单主线程)
4. **LLM 需外部服务** — 需自备 API Key (OpenAI/Claude/GLM 等)
