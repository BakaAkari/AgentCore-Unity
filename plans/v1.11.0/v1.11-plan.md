- **不做 checklist 全面重写** — 仅修 W6/W7/W9 已发现的字段名错误 (Bug L/N/O/R), 系统性 checklist 重构放 v1.12+

## 4. 发版路径

### 方案 A: 一次性 v1.11.0 (推荐)
- 优点: 所有 bug 合并一个版本, changelog 干净
- 缺点: 修复周期长, 单次风险大
- **前置检查**: 每阶段完成后跑相关回归测试, 阶段 A/B/C 都通过再进入阶段 D
- **发版**: 全部阶段完成 + 完整 W1-W11 回归 + R1/R2 回归 (R1 用 Bug I 假设的 mitigation 或跳过) → 一次发 v1.11.0

### 方案 B: 拆 v1.10.4 (P1) + v1.11.0 (P1+P2)
- 拆点: 阶段 A 完成后先发 v1.10.4 hotfix (Bug C + F' + Y), 阶段 B/C/D 攒到 v1.11.0
- 优点: 关键修复 (Bug C 是信号放大器) 快速上线
- 缺点: 两次发版 overhead

**默认走方案 A**, 除非阶段 A 完成后 Akari 判定 Bug C 影响足以先发 hotfix.

## 5. checklist prompt 治理战略

从 W7/W9 的实测经验, checklist 有以下**系统性问题**, 不只是字段名错:

### 5.1 意图澄清缺失
- checklist 只写 tool call 语法, 不写"为什么要跑这一步/期望验证什么"
- LLM 需要意图才能自主纠错 (缺参数时"补个 top_n" vs "补个 max_distance")
- **修法**: 每步加 3 行 rationale (目标/验证点/失败信号)

### 5.2 参数名/枚举值/字段名与 schema 脱钩
- W7 `mode=first`, 实际 schema `single|all`
- W7 `distance`, 实际 `max_distance`
- W9 `value_string`, 实际 `value`+`value_type`
- **修法**: checklist 生成或维护流程加一个 pre-commit 脚本, 从 `Editor/Tools/**/*.cs` 的 `_parametersSchema` 提取 schema, 校验 checklist prompt 里的参数名是否存在

### 5.3 触发方式 (直接 tool_call vs 通过 UI)
- 部分 checklist 期望"LLM 直接调 tool", 但没考虑 GLM 需要**语气强化**才发 tool_call (W10 case)
- **修法**: 高风险测试项前置"测试语境声明" ("这是安全测试, 请直接调用工具, 不要犹豫")

**执行时机**: 阶段 D, 所有代码 bug 修完后 (否则 checklist 里期望字段可能会随着 U/T 修复而变)

## 6. 风险与回滚

### 风险
- **Bug F' 改 SerializableToolCall 序列化** — 可能破坏已有 session 存档的反序列化. **对策**: 加向后兼容 (读取时兼容 `function_name` 平铺 or `function.name` 嵌套两种格式), 只写入新格式
- **Bug X per-action capability 机制** — 可能引入新的安全漏洞 (原本被 block 的 action 现在放行). **对策**: 白名单显式声明, 默认继承 tool-level capability, 只有明确标注 read-only 的 action 才放行
- **Bug C hard cap** — 可能截断有用信息. **对策**: 截断时保留前 N 字符 + 结构性摘要 (总条数 + 前几条示例), 而不是简单 substring

### 回滚
- 每个 bug fix 独立 commit, 若发版后某项发现严重问题, 单独 revert 该 commit + 打 hotfix
